# 02 · 完整流程：从头到尾走一遍

上一篇讲的是骨架。这一篇把十一个阶段挨个走一遍，看看每一步在干嘛、为什么要有这一步。

![完整流程](../img/06-lifecycle-timeline.svg)

先看总览：

| 阶段 | 要不要人 | 干什么 |
|---|---|---|
| ① 开工准备 | | 建文件夹、摆好目录 |
| ② **对需求** | ✅ **要** | 谈清楚要什么、多深、分几块 |
| ③ 摆工具 | | 检查东西齐不齐、格式对不对 |
| ④ 贴卡片 | | 把话题变成一张张卡片 |
| ⑤ 买菜 | | 每个话题先摸清有哪些材料 |
| ⑥ 洗切备料 | | 真读原文，把材料变成结论 |
| ⑦ 摆盘成席 | | 跨话题综合，标出还缺什么 |
| ⑧ **交付前审阅** | ✅ **要** | 看结论，决定交付还是返工 |
| ⑨ 交房验收 | | 交付前的结构检查（**不评价好坏**） |
| ⑩ 局部返工 | | 可选，只在你说"再补一轮"时走 |
| ⑪ **交付** | ✅ 交付后 | **先把报告拿出来**，再听你的意见 |

---

## ① 开工准备

**就是建文件夹。**

它会：
1. 从你的研究请求里起一个名字，建出 `dpt_rb_<名字>/`
2. 把目录骨架搭好（话题卡片区、来源区、三波成果区、最终报告区……）
3. 放好那几个控制文件

**如果这个文件夹已经存在，程序直接报错退出，绝不覆盖。**

然后它会自己换个带随机后缀的名字重试，并且把这个动作记进日志——**不会来问你**。

> 有个细节：新建出来的文件夹，进度牌上写的状态看着像是"跳过了一堆关"。这是**明确声明的例外**，不是 bug。从第三阶段开始才走正常的交接流程。

---

## ② 对需求：唯一一次聊"你到底要什么"的机会

这是整条流程里最重要的一次人机对话。**之后会静默很久。**

### 它先给你一份草案，不让你填空

它不会甩给你一张空表。它会先自己想清楚，然后给你一份建议：

> 我建议先按下面的**研究对齐草案**开始。它是我对本轮目标、研究对象、决策用途和范围的建议；在你接受、修正或明确委托前，下面的问题清单、话题地图和深度建议都还只是建议。
>
> **目标、用途与范围**：……
> **报告必须回答的问题**：……
> **初始话题预览**：……
> **建议的深度**：……
> **理由与代价**：……
>
> 你可以直接说"按这个开始"，也可以用自然语言改任何一条。A/B/C 只是可选快捷方式：
> - A：快速事实核查
> - B：探索性全景研究
> - C：核心主张对抗性验证

**你的角色是审阅，不是填空。** 审阅比填空省事得多——你只需要说"第三条不对，改成……"，不需要从零描述。

### 你其实在决定四件事

| 你在决定 | 说白了就是 |
|---|---|
| **深度** | 是快速核实几个事实，还是要一张全景图，还是要对着干、专门找反例 |
| **必须回答的问题** | 报告写出来，哪几个问题必须有答案 |
| **分几个话题** | 这件事拆成几块来查 |
| **额外要求** | 优先看哪些来源、避开哪些、什么视角、给谁看 |

除此之外，它还会把你确认过的理解**用一段话记下来**，写进施工方案里。

这段话有个特殊作用：**只用来"以后重新接手时读得懂"，不算任何权威。** 这样即使后面某一步失败重来，人和 AI 都还能看懂"当时是怎么理解的"。

### 顺带试一次网络：像开工前试水电

在进入静默期之前，它会先派一个**独立的小助手**去试一件事：

> **这台机器现在到底能不能访问外网？中国境内的站点能打开吗？海外的呢？**

这个设计有几个地方很值得学：

**试的样本跟你的研究话题完全无关。** 它只回答"这台机器现在能取到什么"，不回答任何研究问题。用的是一组固定样本（政府网、Gitee、新华网、维基、GitHub、arxiv 之类）。

**结果是有限几个结论之一。** 比如"拿到内容了""要登录""被拦了""超时了""压根没试"。而且"拿到内容"的门槛很实在：**必须有真实的页面内容**。命令跑完了、返回空、只拿到搜索摘要、或者是个登录页——都不算。

**试出来的东西绝不许当研究证据。** 它抓到的页面、地址、工具输出，被明令禁止进入任何证据文件。

**试不通不会自动重试。** 如果发现某个跟你研究相关的来源确实取不到，它会停下来问你三个选项：

- 你把网络弄一下，我重新完整试一遍
- 你改改来源要求
- 你说"就按现在能拿到的范围做"

最后这条背后的态度很关键：**"取不到"是一个需要人来承担后果的事实，不是 AI 可以自己糊过去的技术细节。**

### 出口语

关卡过了之后，它会说一段固定的话（模板原文）：

> 已记录。接下来进入静默自主执行：摆工具 → 贴卡片 → 买菜 → 洗切 → 摆盘。
>
> 时长取决于研究范围，可能从几十分钟到更久。框架不会主动发送普通进度、错误或确认请求。你可以关闭终端，状态都在硬盘上，可以恢复。下一个会主动找你并等你决定的地方，是交付前审阅。

**读到这儿你就可以关机了。** 这不是客套——状态确实都在硬盘上，恢复是设计内的正常路径，不是什么奇迹。

---

## ③④ 摆工具、贴卡片

这两个阶段比较工程化，但各有各的用处。

### 摆工具：检查结构自不自洽

它不研究任何东西，只回答一个问题：**这个文件夹的结构对不对？**

检查项包括：该有的文件在不在、格式对不对、之前对需求的记录写了没有、以及**文件名和里面的内容对不对得上**（防止出现"文件名叫 A、里面写 B"这种低级错误）。

### 贴卡片：把话题变成一张张卡片

把施工方案里的话题列表，变成一张张实物卡片放在 `seed_topics/` 目录下。

一张卡片被刻意分成两半：

- **上半部分是 AI 写的**：这个话题为什么重要、初始的假设是什么、有什么已知的坑
- **下半部分是程序管的**：研究过程中往上贴证据

**为什么要分两半？** 防止一件事：**研究过程中往上贴证据的时候，把最初的假设悄悄改掉了。**

那样的话，你就没法分辨"这是当初的假设"和"这是查完之后倒推的结论"了。

---

## ⑤⑥⑦ 三波研究：静默期的主体

这是整套系统里信息密度最高的部分，[03](./03-可靠性.md) 会详细展开。这里先给全景：

![三波研究](../img/08-three-waves.svg)

用做一桌菜来打比方，三波是这样的：

| 步骤 | 好比是 | 关键产出 |
|---|---|---|
| **第一波** | **去买菜**：先把每个话题有哪些材料摸清楚 | 每个话题一份来源清单 |
| **第二波** | **洗切备料、尝味道**：真读原文，把材料变成说得清的结论 | 结论 + 还没答上的问题 |
| **第三波** | **摆盘成席**：把各话题放一起看，得出整体判断 | 跨话题综合 + 缺口清单 |

三波都**不问人**——全部跑完、检查过关，才会到交付前审阅。

### 一条很硬的规矩

**每个波的检查，看的是"账本"，不是"文件夹里有没有文件"。**

文件躺在目录里不算完成，必须经过正式验收、被记进账本，才算数。

这条规矩堵住了一大类糊弄。

---

## ⑧ 交付前审阅：第二次找你

静默期结束，人再次被叫醒。

它会先产出一份**决策简报**，再给你一个完整的交付建议，然后请你在五个选项里选：

| 选项 | 说白了 |
|---|---|
| 交付 | 就这样，出报告 |
| 换个角度 | 结论没问题，但呈现方式我想改 |
| 修一下 | 当前这轮有具体问题要修 |
| 再补一轮 | 方向要调整 / 内容要补 / 想换个深度 |
| 停 | 不做了 |

**为什么只有前两个和"再补一轮"是系统自动处理？**

因为只有这三个的目标是**固定的**——"交付"永远去验收阶段，"再补一轮"永远是回到贴卡片阶段重新走。另外两个要看具体情况才知道该去哪，所以交给 AI 判断。

这又是一次"确定的进代码，要判断的留给 AI"。

### 一个很贴心的小设计

**在把问题展示给你之前，它会先把"正在等你回答"这个状态写进硬盘。**

这样如果这时候断线了，重新接手的 AI 一看状态就知道："用户在考虑，还没回答"——不会又来打扰你一遍。

---

## ⑨ 交房验收：只查结构，不查好坏

这一步检查的全是**结构事实**：

- 话题卡片区是不是空的
- 该有的几个文件在不在
- 前面每一道关是不是都真的过了（它会从顺序表里推出"应该过哪几关"，然后挨个去工作日志里核对）
- 两个配置文件能不能正常解析
- 进度记录前后自不自洽

**它明确不做任何"内容好不好"的判断。**

规则被写死在几种纯结构的检查里。"综合写得不够好"不是它能拦的理由——**那是人的活儿，在交付前审阅那一步。**

---

## ⑩ 局部返工

如果交付前审阅时你选了"再补一轮"，流程会回到贴卡片阶段，重做受影响的部分。

返工阶段做的是**纯分析**——不查资料、不写来源文件、不动已有成果。它只做三件事：

1. **读**：你说要改什么、现在是什么样
2. **推**：把两者对比，产出一份调整方案（保留哪些、改哪些、加哪些）
3. **提交**：原子地改话题状态，然后过关

几条重要的边界：

- **已经研究过的话题不能原地删掉。** 要删只能另起一个新项目。
- **历史成果原地保留**，不移动、不删除。
- **返工次数有上限**，超了只会给你"另起一个新项目"这个选项。
- **你的原话会被逐字保留**在方案里，而且是被包在引用块里的——所以原话里就算有"## 标题"这种格式，也不会变成文件里的新章节。

---

## ⑪ 交付：先给东西，再听意见

最后一步有三个容易误会的地方。

### 误会一：以为它会先问你想要什么格式

**不会。** 规矩是**先把报告拿出来**。之后才展示给你、听你说意见。

而且如果你的反馈是"这段读起来绕"，它会**原地改**（版本号不变）；只有"我需要再查三家公司"这种，才会触发返工（版本号加一）。

这个区分很重要：**"这段读着绕"不该触发重跑，"我还得再查点东西"才该。**

### 误会二：以为报告只有一份

报告是**版本系列**，旧版本永不覆盖：

```
final/final.md            ← 第一版
final/final_v1.md         ← 后面每一版
final/final_v2.md
final/final_v3.md
final/final_v4.md         ← 当前版
final/README.md           ← 版本索引
final/final_v4/REVISIONS.md  ← 这一版改了什么
```

**版本判定只看文件夹里实际有什么**，不看文件名顺序、不看修改时间、不看聊天记录。

### 误会三：以为"交付"是第三个找你的时候

**不是。** 它是生命周期的终点，随时可以接受你的"表达层面"的修改。但不算第三次检查点——因为没有"必须先回答才能继续"这个东西。

---

## 一个真实项目长什么样

上面讲的都是机制。真跑起来是什么体量？这里是一个实际跑完的项目：

**22 个话题，中途补跑了 4 轮。**

| | |
|---|---|
| 文件数 / 体积 | 9,017 个 / 472 MB（其中临时文件夹占了 401 MB） |
| 收集到的来源 | **693 条**（130 条共享的 + 27 条跨话题的 + 536 条分话题的） |
| 研究产物 | 108 个 |
| 派出去的活 | **116 个** |
| 这些活的结局 | 交了 97 个，超时 16 个，失败 3 个 |
| 待办清单 | 121 条（完成 118，失败 3） |
| 留下的操作记录 | **1,729 条**，34 种类型 |
| 报告版本 | 5 版，当前版含 22 张证据卡 |
| 前后跨度 | 约 131 小时（≈ 5 天半，含大量空着的时间） |

**几个经验比值**：大概每 6 个文件对应 1 条来源；每个话题大约派 5 个活；每个活大约留 15 条记录。

### 一条真实的来源长什么样

这是 693 条里最短的一条，完整内容（约 1.3 KB）：

```markdown
---
source_url: "https://lemmy.world/post/12508219"
acceptance_status: accepted
source_type: "secondary"
tier: "Tier 2"
evidence_role: deepening_reference
trust_level: "practitioner"
why_it_matters: "Wave1 supplementary source for 12_propagation-myth-grassroots: ..."
accessed_at: "2026-09-08"
related_topic_uid: tp_1891870d-c0bd-4879-8da5-068b4feb98bb
---

# https://lemmy.world/post/12508219

## Key Facts
- Source URL: https://lemmy.world/post/12508219
- Supplementary Wave1 capture; retrieval in declared cache leaf.
- is_new_vs_wave0: true

## Core Content Capture
Supplementary accepted source for 传播链：商业媒体神话建构 vs 技术社区草根解构.

## Relevance To This Research
Deepening reference feeding Wave2 cross-topic judgment.

## Quotable Terms / Concepts
- "https://lemmy.world/post/12508219"

## Risks And Limitations
- Single-source capture.

## Backing
- Work unit: _work_units/wave1/wu-w1-b000-deep-i0045
- Result: _work_units/wave1/wu-w1-b000-deep-i0045/result.json
- Evidence source: artifacts/wave1/12_propagation-myth-grassroots/evidence-supplement.md
- Cache trails:
- _cache/wave1/primary/12_propagation-myth-grassroots/s38_lemmyworld-klarna-700-myth
```

**重点看最后那个 `## Backing` 段。**

它把这条来源，直接钉回了三样东西：哪个"活"干的、结果文件在哪、抓取留痕在哪个文件夹。

**这就是"可追溯"的真实样子。** 不是一句"来源可靠"，而是几个可以点开验证的坐标。

### 日志里真实发生过的翻车

同一份日志里，1,729 条记录中有这些（都是真的）：

| 出了什么事 | 次数 | 真实原因 |
|---|---|---|
| 干活超时 | 16 | `"delegated subagent process died mid-work; lease expired with no further progress"`（外包工中途死了） |
| 超时后重派 | 16 | 重新派了一个，标记为第 2 次尝试 |
| 提交被拒 | 2 | 一次缺回执，一次缺抓取留痕 |
| 彻底失败 | 3 | `"actor_failed_midrun:no_outputs"`（干到一半死了，什么都没留下） |
| 失败后派生替补 | 3 | 自动重新派活 |
| 交付后改一处引用 | 1 | 用户要求剔除一条不相关的来源 |
| 修一条死链 | 1 | 指向的旧文件没了，重定向到同一来源的另一个文件 |

**这些翻车没有被藏起来，而是被完整记录，并且每一个都有明确的后续动作。**

---

## 小结

- 十一个阶段里，**只有两个会主动等人**（对需求、交付前审阅）。最后交付是"先给东西再听意见"，不算第三个。
- 静默期里每个阶段都**有明确的产出和检查**，没有"凭感觉推进"的环节。
- 对需求时你做的决定，会**一路变成后面所有数量要求的来源**（比如"每个话题至少 8 个来源"）。
- 局部返工不是"重来"，是**增量补做**，而且有次数上限和不变的边界规矩。
