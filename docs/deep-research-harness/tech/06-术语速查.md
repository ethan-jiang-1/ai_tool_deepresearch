# 06 · 术语与速查

前面六篇讲原理。这一篇是工具页：**查名词、查命令、以及如果你要自己搭一套可以抄什么。**

---

## 一、术语表

怎么看这张表：**第一列是你平时会怎么想这件事，第二列是代码里叫什么，第三列是大白话解释。**

### 文件和数据放哪

| 你会怎么说 | 代码里叫 | 说人话 |
|---|---|---|
| 项目文件夹 | run bundle | 一次研究在硬盘上的全部资料，名字形如 `dpt_rb_xxx/` |
| 本次的工地 | current run bundle root | 这次操作选中的那个项目文件夹 |
| 工具箱 | framework root | `DEEP_RESEARCH_HARNESS/`，只读，不装项目数据 |
| 敲命令的地方 | repo command root | 仓库根目录，只是个位置 |
| 草稿区 | `_tmp/`、`_scripts/` | 跑研究时写的临时脚本和草稿，跟着项目一起归档 |

### 流程本身

| 你会怎么说 | 代码里叫 | 说人话 |
|---|---|---|
| 阶段 | phase | 流程里的一步，有自己的说明书和验收 |
| 说明书 | node | 就是那个 Markdown 文件 |
| 顺序表 | `manifest.json` | 一共几步、每步过哪道关 |
| 路由表 | `transitions.chain.json` | 过关之后去哪，**故意写得不全** |
| 要不要等人 | `stop` | `yes` 等人，`no` 自己干 |
| 必须一起读的规矩 | `requires` | 进入这个阶段要加载哪些规则文档 |
| 允不允许自己查 | `search_policy` | 有些阶段压根不许搜 |

### 检查关卡

| 你会怎么说 | 代码里叫 | 说人话 |
|---|---|---|
| 验收关卡 | Gate | 一道机器执行的检查，判定过不过 |
| 关卡规则清单 | gate definition | 声明这道关要检查哪些项 |
| 下一份说明书在哪 | `check.next` | 检查通过时给出的下一个阶段，**唯一的翻页依据** |
| 翻页 | `enter-phase` | 真正打开下一份说明书 |
| 记一笔"上一关过了" | `advance-status` | 只记状态，**不是翻页** |
| 交接证据 | route-bound handoff witness | 日志里"某关过了 + 确实打开了它指定的下一个"的配对记录 |
| 结构化下一步 | `hints[]` | 检查没过时给的行动指令：谁负责、缺什么、重跑哪条 |
| 谁负责 | `repair_kind` | 只回答"该谁修"，**不回答"要不要打扰用户"** |
| 法证 / 建议 | `inspect[]` / `advice[]` | 给人看的细节，**不是行动指令** |
| 带着债放行 | `degraded` | 数量差一点时允许放行，但会记账 |
| 三次必换招 | fatigue | 同一个问题连续失败三次 |
| 查表查不到 | `no_transition` | **正常结果**，不是错误；后续交给判断 |
| 上一关 / 下一关 | `current_gate` / `next_gate` | 进度牌上的状态窗口 |
| 我读到哪了 | `current_node` | 恢复时**该看这个**，而不是只看上一关 |
| 整体状态 | `state` | 未开始 / 进行中 / 卡住 / 已完成 |

### 派活

| 你会怎么说 | 代码里叫 | 说人话 |
|---|---|---|
| 需求单 | queue demand | "还需要做什么"，编号是需求编号 |
| 需求编号 | `queue_item_id` | 要什么（一件事只有一个） |
| 派工单 | work unit | 一个需求的一次执行 |
| 派工编号 | `work_id` | 这一次谁在做，**只有程序能分配** |
| 尝试序号 | `attempt_index` | 同一需求的第几次（**不在派工编号里**） |
| 事务号 | `tx_id` | 一次完整操作 |
| 一次性凭据 | `receipt_nonce` | 防伪造的随机串 |
| 身份证明 | `_beacon.json` | 不可修改的绑定文件 |
| 执行者标记 | `actor_execution` | 逻辑记录：这次是外包工还是主 AI 兜底 |
| 并发上限 | `delegated_concurrency_cap` | 默认 12，**程序不读它，是自律** |
| 活动区 / 补充池 | `active_window` / `refill_pool` | 前面处理的（上限 20）/ 排队的 |
| 在飞 | `delegated_in_flight` | 派出去还没收回来的 |
| 抓取留痕 | cache leaf | 一个来源的留痕文件夹，里面三个文件 |

### 验收和恢复

| 你会怎么说 | 代码里叫 | 说人话 |
|---|---|---|
| 演练 | `dry-submit` | 预演，**什么都不改** |
| 正式交 | `submit` | **唯一的成功边界**，会记账 |
| 迟到还能收 | `late-submit` | 唯一被设计出来的补救口，只针对超时 |
| 保留旧账重派 | `supersede` | 交了之后事实漂移了，派个新活 |
| 重建账行 | `recover-declaration` | 账记丢了但能精确重建 |
| 结算流水账 | `recover-transaction` | 证据完整时把未定的事务结掉 |
| 超时预检 | `timeout-preflight` | 只看不改，给六种建议之一 |
| 你现在该干什么 | `recovery_action` | 固定的十来种之一，永远给一个确定的下一步 |
| 死路 | `missing_contract` | **停下**，不许手工改任何东西 |
| 不许替换 | `semantic_boundary` | 停：光凭内容更丰富，不构成替换旧账的授权 |
| 执行者身份已验证 | — | **硬编码为"否"**，系统不声称能验证这个 |

### 研究内容

| 你会怎么说 | 代码里叫 | 说人话 |
|---|---|---|
| 话题清单 | topic registry | 施工方案里的那个数组，话题的唯一依据 |
| 话题卡片 | seed topic | `seed_topics/xxx.md`，上半 AI 写、下半程序管 |
| 话题身份 | `topic_uid` | 不可变的话题编号 |
| 三波 | wave0 / wave1 / wave2 | 买菜 / 洗切备料 / 摆盘成席 |
| 一条发现 | finding | 第三波得出的跨话题结论，编号形如 `W2F-021` |
| 这条还缺不缺东西 | `gap_status` | 缺口状态，必须交代清楚 |
| 来源申报 | `source_claims[]` | "哪个网址支撑了哪条结论、留痕在哪" |
| 深度审查 | `depth-review.yaml` | 每个话题的"够不够深"决策文件 |
| 先看看有没有已交的 | convergence | 数量不够时，先问"还有没有交了但没登记的" |
| 出处表 | Evidence Map | 报告里的三列表：编号 / 结论 / 出处 |
| 交付契约 | `composition_handoff` | 交付前审阅定下的：给谁看、什么用途、怎么呈现 |
| 不该有的成品 | `premature_final_present` | 没到交付阶段就有了报告文件，会阻断检查 |

## 二、命令速查

全部从**仓库根**执行。退出码三态：

| 码 | 意思 |
|---|---|
| 0 | 成功 / 检查通过 |
| 1 | 没过（可修） |
| 2 | 命令敲错了 |

### 建项目

```bash
# 新建（屏幕输出的是文件夹绝对路径，方便脚本接）
B=$(node DEEP_RESEARCH_HARNESS/cli/instantiate-run-bundle.mjs <名字>)

# 校验控制文件（注意是直接跟路径，不加 --bundle）
node DEEP_RESEARCH_HARNESS/cli/validate-bundle.mjs "$B"

# 看目录结构
node DEEP_RESEARCH_HARNESS/cli/inspect-bundle.mjs "$B" --summary
```

### 翻页和记状态

```bash
# 打开下一份说明书（唯一的翻页方式）
node DEEP_RESEARCH_HARNESS/cli/enter-phase.mjs --bundle "$B" --node phases/phase-setup.md

# 记下"上一关过了"（不是翻页）
node DEEP_RESEARCH_HARNESS/cli/advance-status.mjs --bundle "$B" --to hitl1_recorded

# 查有没有跑偏（只报告，不修）
node DEEP_RESEARCH_HARNESS/cli/audit-phase-status.mjs --bundle "$B"

# 查能不能接着走
node DEEP_RESEARCH_HARNESS/cli/check-reentry.mjs --bundle "$B" --at wave1_complete

# 重建施工方案里的进度段（只影响展示）
node DEEP_RESEARCH_HARNESS/cli/reconcile-plan-progress.mjs --bundle "$B"
```

### 过检查

```bash
# 先跑无副作用的预检（研究阶段）
node DEEP_RESEARCH_HARNESS/cli/inspect-wave1-output.mjs --bundle "$B"

# 再跑正式检查
node DEEP_RESEARCH_HARNESS/cli/gates/check-gate-wave1-complete.mjs \
  --bundle "$B" --current-node phases/phase-wave1.md

# 重试时可以自己报次数（系统会和自己数出来的取大的）
node DEEP_RESEARCH_HARNESS/cli/gates/check-gate-wave1-complete.mjs \
  --bundle "$B" --current-node phases/phase-wave1.md --attempt 3
```

## 三、十个可以照搬的原则

如果你要自己搭一套类似的系统，这十条按重要性排：

### 1. 状态记在硬盘上，不靠记性

**做法**：控制文件 + 只许往后加的操作日志 + 账本。
**自测**：随时杀掉进程、清空上下文，重新读文件还能不能接着走？

### 2. 把"谁说了算"从模型手里拿走

**做法**：检查是独立程序，规则写死在配置和代码里。模型不能改状态、不能写账。
**自测**：模型"觉得完成了"和"系统认为完成了"，是不是同一件事？

### 3. 完成必须能被翻译成机器能核对的东西

**做法**：每个阶段有明确的产出清单 + 数量要求 + 格式检查。
**自测**：能不能写一个完全不懂业务的程序，来判断"这步做完了没有"？

### 4. 分清"文件在那儿"和"证据成立"

**做法**：账本 + 抓取留痕 + 权威性判定。检查读账，不读目录。
**自测**：往目录里扔个文件，能不能骗过验收？

### 5. 人只放在该放的位置，而且只放两个

**做法**：开工前对需求、交付前审阅。中间全静默。**给草案让人审，不给空表让人填。**
**自测**：人花的时间是在做判断，还是在做机械确认？

### 6. 静默是契约，不是态度

**做法**：把"要不要等人"做成每个阶段的字段，并且**明令列举**不许做的事。
**自测**：会不会因为"遇到困难"就自动变成"问用户"？

### 7. 出错必须有一个确定的下一步

**做法**：错误用固定的枚举表达；没过的时候给结构化的"谁负责、缺什么、重跑哪条"。
**自测**：失败时 AI 是"知道该干嘛"，还是"开始自己发挥"？

### 8. 但也要有一条明确的"停"的边界

**做法**：把"没有合法路径"做成一等公民。禁止手工改权威文件，禁止平行成功路径。
**自测**：系统会不会为了"看起来成功"而伪造状态？

### 9. 并发要有身份、事务和幂等

**做法**：需求身份 ≠ 执行身份；一把全局锁；改前登记、改后查包；同内容幂等、异内容拒绝。
**自测**：两个工人同时干活会不会互相覆盖？重试会不会产生两笔账？

### 10. 降级、失败、缺口，都要如实记录

**做法**：降级要标注并记成债；失败要进日志；缺口要有明确处置，不许悄悄忘掉。
**自测**：事后能不能从记录里看出"当时哪里没做到位"？

## 四、常见误解

| 你可能以为 | 其实 |
|---|---|
| 说明书里写了就生效 | **说明书不是权威**。只有检查程序跑出来的结果算数 |
| 索引目录里有，就是可信来源 | 索引只是导航，**不是证据** |
| 文件放在 `reference/` 里就算证据 | 必须能追溯回正式验收过的产出 |
| 看"上一关过了"就知道该读哪份说明书 | 该看"我读到哪了"。这俩是两个不同的东西 |
| "记状态"那条命令可以用来翻页 | **不行**。翻页只有一条命令 |
| 检查没过说明出事了 | 没过是**正常的检查结果**，"查表查不到"也是正常的 |
| 检查通过就说明质量过关 | 只说明**结构**过关。质量是人判断的，带债通过还欠着账 |
| 并发上限 12 是程序强制的 | 是**自律**，程序代码根本不读这个字段 |
| 系统能验证助手真的在跑 | 不能。返回里明确写着"未验证执行者身份""未证明存活" |
| 交付前它会问我想要什么格式 | **不会**。先给报告，再听意见 |
| 中途提问会打断流程 | 不会。它会回答，但**这次回答不算数** |
| 超时了就白干了 | 超时有一个（条件很严的）"迟到还能收"的口子 |
| 失败的活可以手工补一笔账 | 明令禁止。只能走那几个合法的恢复命令 |

## 六、最后

回头看，这套系统的想法其实很朴素：

> **别指望 AI 更聪明。把"聪明"之外的事情——顺序、状态、权限、边界、记账——全部搬到确定的地方去。**

它换来的东西也很具体：

- **可追溯**：每条结论能倒推回来源
- **能续上**：随时中断都能接着走
- **能并发**：多话题同时开工而不打架
- **造不了假**：AI 没法自己宣布成功
- **跑得住**：几天不用人管
- **出错有解**：知道该谁修、怎么修、重跑哪条
- **人只做人的事**：做判断，而不是数文件

而且它很诚实地说明了自己**做不到什么**——并发上限靠自律、执行者身份没法验证、有几条规则纯靠自觉。
